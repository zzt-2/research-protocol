## §sim 仿真器设计确认 + 标准文档阅读

> 不做会出什么问题：从 baseline 选定直接跳到实现，中间缺少关键设计决策。星座规模、信道模型精度、切换粒度等决定影响所有后续实验。

### 操作

1. **确定仿真器核心参数**（根据研究方向和论文实验设置）：
   - 卫星通信：星座规模（卫星数、轨道面数）、信道模型精度、切换决策粒度
   - 通用：数据集规模、评估场景列表、随机成分清单
   - 参数来源：优先参考精读论文的实验设置，其次参考 ITU-R 标准

2. **阅读标准文档/基础教材**（论文引用但未给实现细节的）：
   - 论文中出现 "according to 3GPP TR XX.XXX" 或类似引用 → 找对应标准文档
   - 只读与实现直接相关的章节，不读全文
   - 提取关键参数和流程定义，记录到 `decision_log.md`

3. **生成仿真器设计规格**，包含三节：
   - **模块清单**：每模块写明功能和引用的标准/论文
   - **关键参数表**：参数 | 值 | 来源 | 理由
   - **验证标准**：解析验证（已知参数→解析公式）、统计验证（分布/自相关/功率谱密度）、退化测试（去随机→确定性）

4. **设计奖励函数**（参见 `domain-comms.md` §1.5 奖励函数设计规范）：
   - 从精读笔记的"实现关键细节"字段提取各论文的奖励归一化方式
   - 确定本项目的奖励结构、归一化策略、权重比例
   - 列出各项的典型值范围，确保无量级失衡

5. 参考技术栈和模块建议见 `domain-comms.md`

### 质量门槛
- 仿真器设计规格包含完整的模块清单、关键参数表、验证标准
- 奖励函数设计包含量级分析

1. 仿真器设计规格（模块清单完整性、参数合理性、验证标准充分性）

## §impl 仿真环境搭建 + Baseline 复现

**执行者**：[MUST] 子 agent 或独立对话执行，主线程只收结果

### Part A：仿真环境搭建 + 验证

> 不做会出什么问题：仿真器缺少关键模块会导致数据过于平滑，DL 方法优势被简单方法覆盖，直到实验很久后才发现，造成大量返工。

**默认路径**：自建仿真器（纯 Python）。推荐技术栈和仿真器模块参考见 `domain-comms.md`。

#### 验证清单（全部通过方可继续）

- [ ] **解析验证**：已知参数下输出与解析公式一致（如自由空间损耗 L = 20log(4πd/λ)）
- [ ] **统计验证**：生成数据的统计特性符合预期（分布、自相关、功率谱密度）
- [ ] **退化测试**：去掉随机成分后，输出退化为确定性结果
- [ ] **自相关预警**：时序数据 lag-1 自相关 > 0.95 → 发出"过于平滑"警告

自相关预警处理：信道过于平滑时需修复仿真器（引入非平稳特征）。

### Part A-checkpoint：MDP 试运行（奖励合理性检查）

> 不做会出什么问题：奖励尺度失衡导致 DRL 退化为贪心策略，训练几百 episode 后才发现，浪费大量时间。

仿真器验证通过后、训练任何 DRL 之前，必须执行此检查。

1. **跑 1 episode 随机策略 + 1 episode 贪心策略**
2. **奖励分解**：统计各项绝对值占总奖励绝对值的百分比，输出表格（奖励项 | 随机策略 | 贪心策略 | 占比）

#### 质量门槛（硬性）

- [ ] **无单一项独占**：任何单一项占总奖励绝对值 >95% → **STOP**，修复奖励函数后再继续
- [ ] **策略区分度**：贪心策略 vs 随机策略的总奖励差距 >10%
- [ ] **关键指标可优化**：在目标指标（如阻塞率）上，贪心/随机策略的结果有差异

#### 不达标时

- 单一项 >95% → 通常是量级失衡（如 rate~10⁶ vs penalty~10），需要归一化或调整权重
- 策略无区分度 → 奖励函数可能缺少关键信号，检查是否遗漏了论文中的奖励项
- **修复后重新跑此检查**，通过后方可进入 Part B

> 试跑教训（F5）：rate~10⁶ 占奖励 99.99%，DRL 学到的策略等价于 MVT（贪心选最高 rate）。根本原因是 L029 论文的奖励归一化细节在精读时丢失——精读提取了 r = α·r_th - β·r_blk 的结构，但漏掉了 rate 被归一化到 [0,1] 的关键细节。

### Part B：Baseline 复现

#### 复现定义

"复现"在本项目中定义为：
1. **在自己的仿真环境中实现论文的算法架构和核心设计**
2. **验证相对趋势**：DRL 方法 > 传统方法 > 随机方法
3. **[MUST NOT] 直接对比绝对数值**——环境不同（卫星数、信道参数、UE 分布），数值不可比

复现成功的判断标准：DRL baseline 在关键指标上结构性优于传统 baseline。如果 DRL 未优于传统方法 → 在 `decision_log.md` 记录原因，分析是否为奖励函数/超参问题后再继续。

#### 传统方法实现规范

传统 baseline（B1）的实现 [MUST] 满足以下条件之一：
1. 直接复现论文中描述的传统方法（引用论文 + 章节）
2. 按照标准文档实现（引用标准编号，如 3GPP TS 38.331 for A3 事件）

[MUST NOT] 凭印象实现"传统方法"：
- "选最高信号"不是 A3 事件——A3 需要迟滞（hysteresis）+ 触发时间（TTT）
- "选最高 rate"不是 MVT——MVT 需要计算剩余可见时长（轨道几何）
- 把贪心策略当作传统方法等于建了一个稻草人

#### 操作

1. 根据选定 baseline 的代码/算法描述，在已验证的仿真环境中实现
2. 论文只有图表没有数值时：目视对比曲线趋势（形状、拐点、渐近行为），记录为"图表级验证"
3. 容忍度参考见 `domain-comms.md`

## 不达标时
- 仿真器验证失败 → 根据失败项修复，重新验证
- MDP 试运行不达标 → 修复奖励函数后重新检查
- Baseline 复现失败 → 记录原因到 decision_log，评估是否更换 baseline 或调整研究方向
