# Paper Writing Skill 设计

> 日期：2026-07-14
> 状态：已获用户逐段确认，待 RED/GREEN/REFACTOR 验证

## 1. 目标

建立全局个人技能 `paper-writing`，把论文写作中反复验证过的门控、诊断、证据链、选择性呈现、批量修订、编译检查和独立验证固化为可执行流程。技能安装到 `C:\Users\zzt\.agents\skills\paper-writing`，项目仓库只保存设计与验证证据。

该技能解决的核心问题不是“怎么写得像论文”，而是防止 AI 在篇幅、专业性或逻辑受到质疑时跳过事实核验，直接扩写、润色或调版，制造新的口径漂移和内容垃圾。

## 2. 分层架构

```text
paper-writing/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── references/
    ├── diagnosis.md
    ├── revision.md
    ├── conference-paper.md
    ├── communication-paper.md
    └── verification.md
```

- `SKILL.md`：六状态主流程、四道硬门、转换条件、停止条件和专项技能路由。
- `diagnosis.md`：篇幅不足、专业性不足和逻辑不顺的可执行诊断。
- `revision.md`：问题队列、L1-L6 影响分级、批次处理和一致性检查。
- `conference-paper.md`：短篇会议论文共性，不写死具体会议页数。
- `communication-paper.md`：BER/SNR、信道模型、仿真设置、结果曲线和物理归因等通信领域规则。
- `verification.md`：独立审查项目、PASS/BLOCKED 判据和交付证据。

## 3. 六状态主流程

```text
INTAKE -> DIAGNOSE -> PROPOSE -> WRITE -> VERIFY -> DELIVER
```

| 状态 | 必须产物 | 禁止动作 |
|---|---|---|
| INTAKE | 目标、范围、官方约束、输入版本 | 改正文 |
| DIAGNOSE | 事实测量、根因表、证据指针 | 扩写、润色 |
| PROPOSE | 修改合同、影响清单、退出判据、用户确认 | 实施修改 |
| WRITE | 经确认的批量修改 | 顺手扩范围 |
| VERIFY | 最新构建证据、独立审查结果 | 自审自验后宣布完成 |
| DELIVER | 交付物、未决项、证据摘要 | 隐瞒 blocker |

四道硬门：未核验投稿要求不写；未建立事实矩阵不改；未经用户确认不实施实质改写；未经独立验证不宣称完成。

## 4. 写前诊断门

诊断按固定顺序执行：

1. 冻结现场：记录用户原话、当前源文件、构建产物和版本时间。
2. 事实测量：投稿约束、有效内容页数、各节词数/公式/图表/引用、异常留白、占位符。
3. 基准对照：至少 5 篇同类论文；`3/5` 为明确缺口、`2/5` 为可选、`<=1/5` 不据此添加。
4. 事实矩阵：`论点 -> 数据 -> 对比对象 -> 指标口径 -> 图表/公式 -> 来源`。
5. 论证链：`问题 -> 现有不足 -> 方法 -> 机理 -> 验证 -> 结论`。
6. 根因分类：G0 规则/版本、G1 内容、G2 逻辑、G3 专业、G4 数据实现一致性、G5 组织、G6 排版、G7 定位。
7. 最小验证：每次验证一个假设的一个维度，填写证据和否决条件。
8. 修改合同：列拟改内容、影响位置、证据需求、明确不碰项，交用户确认。

篇幅诊断必须区分 PDF 总页数和有效正文页数。专业性审查必须拆成术语、假设、公式实现、可复现性、参数来源、基线公平、指标口径、引用支撑、结果解释和内部语言残留。逻辑审查必须定位缺边、错序或无证据，不能用顺滑过渡句掩盖缺环。

## 5. 数据呈现边界

- 内部分析完整保留所有结果，不伪造、不改口径、不删除异常、不以换精度制造优势。
- 外部论文围绕核心贡献优先呈现有利且有代表性的证据；不主动展开无关失败、开发过程和不影响核心声称的零增益场景。
- 如果不利事实会改变核心结论、比较公平性、算法实际信息使用方式、指标含义或投稿合规性，则不能隐去；先输出影响判断和最低必要披露方案，交用户确认。
- 禁止把局部优势写成全局优势、把数据交叉点写成设计阈值、把经验观察写成理论保证、用未验证物理归因解释结果。

## 6. 改稿与验证

反馈先登记，满足批次条件后统一分为 L1-L6，按 `L6 -> L5 -> L4 -> L2/L3 -> L1` 从底层到表层处理。L2 以上修改前必须检索所有受影响位置；数字口径必须回查代码或数据源；L4 以上必须回查术语、符号、公式和专题不变量。

VERIFY 必须使用最新源文件重新构建，并由独立上下文检查论点证据、数字口径、公式实现、引用、占位符、匿名要求、实际页数和数据呈现边界。

## 7. 可遵守性设计

- 主 `SKILL.md` 保持短，只加载当前状态对应的参考文件。
- 用门禁产物代替“注意”“应当”等提醒语。
- 用一张贯穿式问题表维护症状、根因、证据、级别、确认、实施和验证状态。
- 关键规则写成 `IF / THEN / BEFORE / ELSE BLOCK`。
- 默认停止：约束冲突、版本错位、证据缺失、定位变化、无来源数字和独立验证失败时不得自动继续。
- 明列反合理化条款，处理“只是润色”“先改一版”“数字看起来合理”“时间紧”等常见绕过理由。

## 8. 验证策略

先以没有该技能的 agent 运行至少 3 个组合压力场景，记录真实违规和合理化话术；再用同一场景测试技能。最低场景覆盖：有效正文不足与截止期压力、只报喜与有效性底线冲突、数字/公式/代码口径冲突、模糊的“不专业”反馈。只有技能能稳定停在正确状态、产出规定门禁材料且不提前修改，才进入交付。
