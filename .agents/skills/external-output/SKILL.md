# 对外研究输出（external-output）

## 核心心智模型

**对外输出 = 把"内部研究语言"翻译成"目标读者能懂的语言"，出门前过审查关。**

为什么需要这个 skill：研究过程中会沉淀大量"内部语言"——流程代号（A4/B11）、自造术语（fair_gain）、内部讨论措辞（"击穿""近亲""兑现"）、未验证的数字、内部简称的文献（"Du PTL 2025"）。这些在内部讨论里高效，但**直接端给外部读者 = 黑话**，导师/审稿人/评委看不懂。

**默认失败模式**（本 skill 要防的）：写对外文档时，把内部状态原封不动端出去，没做"读者第一次接触"的翻译。结果是导师问"A4 切换是什么""fair gain 是什么"——不是导师不懂，是**你没翻译**。

**翻译不是改措辞，是重新假设读者**：读者不知道过去两个月的讨论，每个概念从零讲起。翻译后内部代号消失、自造词有定义或换成领域标准词、数字有溯源、文献用规范格式。

## 0. 这个 skill 该不该上场（边界判断）

**该用**：任何"内部研究 → 外部读者"的输出，包括但不限于：
- 导师简报 / 进展汇报
- 论文 abstract / introduction / conclusion
- 答辩 PPT / 答辩讲稿
- 回复审稿意见 / 回复导师反馈
- 开题报告 / 中期报告
- 给合作者/其他组的说明文档

**不该用**（用了 = 越界）：
- 纯内部记录（session note / handoff / decisions.md）——这些就是内部语言，不用翻译
- 代码注释 / 技术文档——那是给开发者的，不是给研究读者的
- 数据分析报告（给项目内部看的）——除非要发给导师/合作者

**边界判断信号**：产物会不会给一个"没参与过这个研究的人"看？会 → 用本 skill。

## 1. 三个必须先想清楚的问题（写之前）

任何对外输出，动笔前必须回答这三个。答不清 = 没想好就别写。

### Q1 目标读者是谁，懂到什么程度

读者分四档，翻译深度不同：

| 读者档 | 懂多少 | 翻译要求 |
|---|---|---|
| **导师** | 懂大领域，不懂你这两个月的具体术语 | 每个具体术语首次定义，领域常识可不展开 |
| **审稿人** | 懂子领域，但更外行更没耐心 | 比导师更彻底的翻译，摘要必须自包含 |
| **答辩评委** | 跨方向，可能完全不懂你这个点 | 从动机讲起，用类比，少公式 |
| **同行读者** | 懂领域，看论文 | 规范术语 + 标准引用，允许专业缩写（首次展开）|

**最容易错**：默认所有读者都跟导师一样懂。实际审稿人比导师更外行。写之前明确"这版给谁"。

### Q2 这个输出的目的是什么

| 目的 | 产物形态 | 关键约束 |
|---|---|---|
| **汇报 + 请示**（简报/进展报告）| 带问题问老师 | 问题要先做功课（见 rules/asking.md），不能没调研就问 |
| **说服 + 呈现**（论文/答辩）| 展示贡献 | 贡献要诚实标注来源（见 rules/claims.md）|
| **回应 + 修改**（回复审稿/导师反馈）| 逐条回应 | 先确认理解再回复，不脑补老师意思 |
| **说明 + 解释**（给合作者）| 自包含说明 | 假设零背景 |

**目的决定结构**：汇报类必须有"想请老师定的"段；说服类不能有问句；回应类必须逐条对应。

### Q3 哪些内部语言必须翻译（出门前清单）

这是本 skill 的核心。详见 §3 出门审查。动笔前先扫一遍脑子里要写的内容，标出哪些是内部语言。

## 2. 强制工作流

任何对外输出，走这五步。跳步 = 违规。

### 步骤 1：识别读者 + 目的（答 Q1+Q2）
明确这版给谁看、要达到什么。写在产物开头或自留底。

### 步骤 2：列内部语言清单
把要写的内容里所有"内部语言"列出来，分类（见 rules/translation.md 的 6 类）。这一步是为了不漏。

### 步骤 3：逐项翻译
对每个内部语言项，决定怎么翻译（删/定义/换标准词/展开缩写/换措辞/补溯源）。详见 rules/translation.md。

### 步骤 4：数字与声称审查（最易翻车）
产物里每个数字、每个"增益/改善/优于"声称，必须过两关（详见 rules/claims.md）：
- **数字溯源**：这个数哪来的？计算口径是什么？验证过吗？
- **声称边界**：这个增益是相对什么？对照对象是真实 baseline 还是事后诸葛亮？来源是我们的方法还是固有性质？

**这条是 today 切换 bug 教训的直接产物**——三轮简报把未验证的切换增益当真的报。数字出门前必须查计算口径。

### 步骤 5：出门审查（出门前最后一关）
按 §3 清单逐条过。不过关 = 不能交出去。

## 3. 出门审查清单（强制，不过不能交）

每条对外输出交付前，逐条核对。任何一条 FAIL = 回去改。

| # | 审查项 | 怎么查 | FAIL 表现 |
|---|---|---|---|
| **C1** | 无内部流程代号 | 全文搜 A/B/Q 等内部编号 | 出现 A4/B11/Q1 等 |
| **C2** | 自造术语有定义或已换标准词 | 每个非领域标准词查"首次出现有没有定义" | fair_gain 无定义直接用 |
| **C3** | 缩写按实际阅读顺序首次展开 | 顺序检查标题、摘要、图、图注、正文 | 图中先出现 HD-FEC，正文后面才解释 |
| **C4** | 数字有溯源（计算口径 + 数据来源）| 每个数字标"哪来的怎么算的" | 切换 +0.27dB 不知怎么算的 |
| **C5** | 增益声称的对照对象是真实 baseline | 每个"优于 X"查 X 是不是真实方法 | vs max(DA,NDA) 事后诸葛亮 |
| **C6** | 贡献声称诚实标注来源 | "我们提出"vs"固有性质"分清 | 把盲估计固有增益说成我们方法的 |
| **C7** | 文献格式、职责和质量匹配 | 查格式、所支撑声称及同职责更强来源 | 用大量会议文献替代可得的期刊/Transactions 来源 |
| **C8** | 无文学化/内部讨论措辞 | 搜"击穿/兑现/近亲/搞定"等 | 用"击穿"而非"使失效" |
| **C9** | 问问题先做了功课（汇报类）| 每个"想问"查有没有先调研 | 老师刚说完图方向没调研又问 |
| **C10** | 概念自包含（目标读者档能懂）| 假设读者第一次接触，每个核心概念能 30 秒懂 | 导师问"这是什么" |

**C1-C3 是术语翻译，C4-C6 是数字/声称正确性，C7-C8 是格式/措辞，C9 是问问题纪律，C10 是总兜底。**

详见 `rules/exit-check.md`（每条的判定标准 + 正反例）。

## 4. 场景路由（不同产物的变体）

核心翻译+审查统一（§2+§3），不同产物有变体：

| 产物 | 场景文件 | 特有约束 |
|---|---|---|
| 导师简报 | `scenarios/briefing.md` | 带问题问老师 + 问题先做功课 + 标清初步/未定 |
| 论文全文、abstract/intro/conclusion | `scenarios/paper.md` | 论证职责 + 反馈闭环 + 图文/篇幅/元数据终验 |
| 答辩 PPT | `scenarios/defense.md` | 从动机讲起 + 类比 + 少公式 |
| 回复审稿/导师反馈 | `scenarios/reply.md` | 逐条对应 + 先确认理解 + 不脑补 |
| 开题/进展报告 | `scenarios/report.md` | 结构严谨 + 规范引用 |

先 Read 对应 scenarios 文件再动笔。

## 6. 触发时机

**显式触发**（用户说）：
- "写简报" / "给老师汇报" / "写进展报告"
- "写摘要" / "写引言" / "写 abstract"
- "做答辩 PPT" / "准备答辩"
- "回复审稿" / "回复老师"
- "写开题报告"

**隐式触发**（操作触发）：
- 创建/修改 `*BRIEFING*` / `*briefing*` 文件
- 创建/修改 论文正文 .md / .tex（abstract/intro/conclusion 部分）
- 创建/修改 PPT 相关文档
- 写"想问老师"/"请老师"类内容

## 7. 与其他 skill/规则的关系

- **session-governance**：管内部记录（S/H/D/V），本 skill 管对外输出。两者互补——内部用 session-governance，对外用 external-output
- **sim-preflight C4**：C4 管"写的损伤和代码一致"，本 skill 管"对外怎么呈现"。写论文场景两者都触发
- **sim-preflight C1-C8**：实验扎实性自检。本 skill 的数字溯源（C4）依赖实验已经过 sim-preflight
- **thesis-lessons TL-22/TL-29**：重大发现先查 + 估计器先验证。本 skill 的数字审查是这两条在"对外输出"场景的落地
- **profile "主线须带证据链"**：本 skill 的 C4（数字溯源）是这个要求的具体化

## 8. 维护原则

- **演进基于真实翻车事件**：每条规则必须能对应到至少一次真实的对外输出失败（今天的切换 bug = C4/C5，fair_gain = C2，A4 = C1...）
- **不写空话规则**：如果一条规则不能给出正反例，删掉
- **新增规则更新 CHANGELOG**：记"日期 + 翻车事件 + 新规则编号"
- **月度审计**：每月扫最近的对外输出，看有没有新翻车模式没覆盖
