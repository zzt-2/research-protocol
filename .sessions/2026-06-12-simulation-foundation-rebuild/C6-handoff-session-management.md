### 根因分析

1. **状态漂移无自动检测**：_registry.yaml 是纯手工维护，完成后忘改状态
2. **topic-index 只有追加没有冻结**：完成的条目仍然占据恢复时的阅读量
3. **Handoff 大小无约束**：大专题的 handoff 可能超过 500 行
4. **成熟度标签缺失**：无法区分哪些文件是当前活跃的、哪些是历史参考
5. **Handoff 模板缺少"变更传递"段**：参数/公式约定变更在跨对话时丢失

## 1. Handoff 模板改进

### 1.1 当前模板不足

当前全局 CLAUDE.md 中的 Handoff 模板有 8 个段落，结构良好。问题不在模板结构，而在：

1. **缺少"约定变更传递"段**：参数/公式约定变更是最高频丢失类型，但模板没有专门段落
2. **"必读"段没有分级**：thesis-direction-pivot 的 H008 必读列表有 5 个 Tier，但模板本身不要求分级
3. **"已完成边界"缺少明确的状态标记**：容易模糊"做了什么"和"还差什么"
4. **缺少 handoff 大小指导**：H008 长到 707 行，恢复成本高
5. **"接收方验证"是 checklist 但没有最小验证集**：6 条 checklist 在实际恢复中往往被跳过

### 1.2 具体改进

#### 改进 1：新增"约定变更"段（mandatory）

在"已完成边界"和"不要做什么"之间插入：

```markdown
## 约定变更（自上次 handoff 以来的关键变更）

- [参数] xxx: 旧值 → 新值（原因：xxx，影响范围：xxx）
- [公式] xxx: 旧定义 → 新定义（原因：xxx，影响范围：xxx）
- [信号模型] 无变更
- [评估方法] 无变更

无变更时写"无关键变更"。
```

**为什么**：参数/公式约定变更是 13 例 handoff 丢失中最高频的类型。没有专门的段落，变更信息会散落在 handoff 正文各处，恢复时被遗漏。

**大小控制**：此段通常 2-5 行。如果超过 10 行，说明变更太多，应该拆分为更小的 handoff。

#### 改进 2："必读"段强制分级

将模板中的"必读"改为：

```markdown
## 必读

### 必读-恢复（3 个以内，恢复上下文必须读的）

1. [文件路径] — [一句话说明为什么必须读]

### 必读-执行（开始工作后需要读的）

4. [文件路径] — [用途]

### 参考（背景信息，按需）

5. [文件路径] — [什么时候需要参考]
```

**为什么**：H008 的 5 Tier 必读列表设计很好，但应该标准化为模板要求。恢复时只读前 3 个文件即可重建上下文，其余在工作时按需读。

**大小控制**：必读-恢复 3 个以内。如果需要超过 3 个文件才能恢复上下文，说明上下文分散度太高。

#### 改进 3：Handoff 大小指导

在模板注释中添加：

```markdown
<!-- 大小指导：正文建议 ≤200 行。超过 300 行应考虑拆分。
     "约定变更"段 ≤10 行。"必读-恢复" ≤3 个文件。
     如果专题很大，在 topic-index 的"当前位置"段写一句话摘要，
     handoff 只写增量变更，不重复 topic-index 已有内容。 -->
```

**为什么**：H008（707行）和 topic-index（553行）加起来 1260 行，恢复成本极高。约束大小迫使写作者聚焦增量信息。

#### 改进 4："接收方验证"最小验证集

将 6 条 checklist 精简为 3 条强制 + 3 条可选：

```markdown
## 接收方验证

### 强制（恢复后必须完成）

- [ ] 已读取 topic-index 的不变量段落
- [ ] 已验证本文件中的约定变更段（如有变更，确认理解影响范围）
- [ ] 已确认当前范围未违反"明确不含"

### 可选（执行前完成）

- [ ] 已验证至少 1 条关键事实声称（列出验证了哪个）
- [ ] 已检查 depends_on 专题的状态
- [ ] 已确认必读-恢复文件均已存在且可读
```

**为什么**：6 条全部强制在实际执行中被跳过。精简到 3 条关键项提高执行率。其中"约定变更"验证直接针对最高频丢失类型。

### 1.3 上下文恢复标准化格式

当对话发生压缩/续接需要恢复时，恢复输出应包含以下段落的精简版：

```markdown
## 上下文恢复摘要（≤200 行）

### 1. Dead Ends（最高优先级）
[被否决的方向和原因，2-5 条]

### 2. 活跃约定
[当前有效的关键参数/公式/信号模型约定，5 条以内]

### 3. 当前位置
[topic-index "当前位置"的复述 + 本 handoff 的增量]

### 4. 范围边界
[不变量 + 明确不含，直接从 topic-index 复制]

### 5. 立即可执行的下一步
[从 handoff "下一轮"复制]
```

**为什么**：当前全局 CLAUDE.md 的恢复格式有 8 段，对 .sessions/ 专题来说太重。精简到 5 段，优先传递"不要做什么"（Dead Ends）和"当前约定"（活跃约定），正是跨对话最容易丢失且最致命的信息。

## 2. _registry 维护规则

### 2.1 状态变更触发条件

| 转换 | 触发条件 | 谁负责 | 何时执行 |
|------|---------|--------|---------|
| new → active | 创建新专题目录 | 开专题的对话 | 创建目录时同步注册 |
| active → dormant | 连续 3 个对话未续接，或用户明确说暂停 | session-governance skill 检测或对话结束时 | 续接检查时 |
| dormant → active | 续接 dormant 专题 | 续接对话开始时 | 读 topic-index 后 |
| active/dormant → closed | 目标已达成，或用户明确放弃 | 完成专题的对话 | 写最后一个 S### 或 H### 时 |
| closed → 不变 | closed 不可逆转 | — | — |

### 2.2 防止状态漂移

**机制 1：session-governance skill 自动检查**

在 session-governance skill 触发时（写 handoff、开新 session），增加一步检查：

```
1. 读 _registry.yaml
2. 对每个 active 专题：
   a. 读 topic-index.md 的"当前位置"段
   b. 如果包含"完成"/"已关闭"/"已废弃"等关键词，建议标记为 closed
   c. 如果 last_updated 距今 >7 天且无明确"进行中"标记，建议标记为 dormant
3. 将建议输出给用户确认
```

**机制 2：YAML 结构校验**

在 session-governance 中增加 YAML 合法性检查：
- 检测重复键（当前 thesis-chapter-fixes 有这个问题）
- 检测未注册目录（对比磁盘目录和 registry 条目）
- 检测 closed 专题的 depends_on 是否仍被 active 专题引用

**机制 3：开新专题时的前置检查**

开新专题时必须：
1. 查 registry 有无同方向未 closed 专题
2. 查磁盘有无未注册目录
3. 确认 depends_on 专题已 stable（active 且近期有更新）

### 2.3 定期审计频率

| 审计类型 | 频率 | 方法 | 触发条件 |
|---------|------|------|---------|
| 状态一致性 | 每 5 个对话 | session-governance 自动 | 写 handoff 时 |
| 文件大小 | 每 10 个对话 | 统计行数 | 最大专题 >10000 行时 |
| 未注册目录 | 每次开新专题 | 对比磁盘 vs registry | 开新专题时 |
| ROT（冗余/过时/琐碎） | 每 10 个对话 | 人工 + topic-index 冻结检查 | 专题成熟后 |

**为什么是 5/10 而不是更频繁**：用户要求"不消耗心力"。每次都审计成本太高，5/10 的频率足以在问题失控前发现。

## 3. 恢复成本控制机制

### 3.1 大型专题的恢复成本控制

thesis-direction-pivot（108文件/23653行）是极端案例。控制恢复成本的核心原则：

**原则：恢复时只读活跃内容，不读历史。**

具体机制：

#### 机制 1：topic-index 分区

topic-index.md 内部分为两个可见区域：

```markdown
## 活跃区域（恢复时必读）

### 不变量
[当前有效的不变量，5-10 条]

### 当前位置
[1-2 句话说明当前做到哪了、下一步做什么]

### 活跃约定
[当前有效的关键参数/公式约定，5 条以内]

---

## 历史区域（恢复时跳过，按需查阅）

### 进展线索
[S001-S026 全部条目...]

### 已确认结论（其他结论）
[历史结论...]

### 范围边界
[完整范围定义...]
```

**恢复路径**：只读"活跃区域"（约 20-30 行），跳过"历史区域"。历史区域在需要具体上下文时按编号查阅。

**大小控制**：活跃区域 ≤50 行。如果超过，说明当前上下文太复杂，应考虑拆分专题。

#### 机制 2：文件成熟度标签

在 topic-index 的进展线索中，为每个条目标注成熟度：

| 标签 | 含义 | 恢复时是否读取 |
|------|------|--------------|
| DRAFT | 正在进行的工作 | 是 |
| ACTIVE | 最近完成的、结论仍直接影响当前工作 | 是（读摘要） |
| FROZEN | 结论已固定，不再变化 | 否（按需） |
| ARCHIVED | 历史工作，仅供回溯 | 否（按需） |

**应用示例**（thesis-direction-pivot）：

```markdown
### S001: 导师会议要点与新方向框架 [FROZEN]
> 2026-05-29 | 方向确定 | 完成

### S019: Ch2 推导+验证 [FROZEN]
> 2026-05-30 | 完成

### S026: 仿真体系统一化+Ch4审计 [ACTIVE]
> 2026-05-31 | 完成 | 结论直接影响当前代码重构

### 当前位置 [DRAFT]
> Ch3/Ch4 审计完成，准备开题写作
```

**为什么**：恢复时只需读 DRAFT 和最近 2-3 个 ACTIVE 条目的摘要。FROZEN/ARCHIVED 跳过。对于 thesis-direction-pivot，25 个 S### 条目中约 20 个可标 FROZEN，恢复阅读量从 553 行降至 ~50 行。

#### 机制 3：大型专题拆分标准

当专题满足以下**任一**条件时，应考虑拆分：

- 总文件数 >50
- 总行数 >15000
- topic-index 活跃区域 >50 行
- 恢复时间 >5 分钟（主观感受）
- 存在 2+ 个相对独立的子方向，每个都有 5+ 个文件

**拆分方式**：

1. 在原专题下创建 `decisions.md` 记录拆分决策
2. 原专题标记为 closed（或 dormant 如果可能续接）
3. 新专题在 depends_on 中引用原专题
4. 新专题的 topic-index 继承原专题的不变量
5. 新专题不复制原专题的文件，只在新专题中引用路径

**应用示例**：

thesis-direction-pivot 应拆分为：
- `thesis-direction-pivot`（closed）：方向确定+开题阶段
- `thesis-writing-prep`（dormant/active）：写作准备+文献
- `thesis-simulation`（dormant/active）：仿真开发+验证

实际上部分拆分已经发生（thesis-sim-exploration、thesis-simulation-consolidation），但原始专题没有 closed，导致恢复时仍然面对 108 文件的目录。

### 3.2 文件大小限制和监控

| 文件类型 | 建议上限 | 超限处理 |
|---------|---------|---------|
| topic-index.md | 300 行（活跃区域 ≤50 行） | 冻结历史条目到 ARCHIVED 区域 |
| handoff (H###) | 200 行 | 拆分为多个 handoff 或减少必读列表 |
| session note (S###) | 500 行 | 拆分为 S###a/S###b 或将细节移入 R### |
| research note (R###) | 300 行 | 将详细数据移入附录文件 |
| _registry.yaml | 单条目描述 ≤2 行 | 详细描述移入 topic-index |

### 3.3 topic-index 维护纪律

**增量更新规则**（与全局 CLAUDE.md 一致，此处强化）：

1. 新增 S###/R### 时：
   - 在"历史区域-进展线索"中加一条（1-3 行摘要 + 成熟度标签）
   - 如果产生新不变量或关键约定，更新"活跃区域"
   - 更新"当前位置"为 1-2 句话
2. 续接对话时：
   - 只更新"当前位置"和必要的活跃区域
   - 不重写历史区域
3. 每 10 个对话做一次 ROT 审计：
   - 将已完成的 DRAFT/ACTIVE 条目标为 FROZEN
   - 将不再被引用的 FROZEN 条目标为 ARCHIVED
   - 清理"未决项"中已解决的条目

## 4. 跨对话信息连续性保障

### 4.1 必须在 handoff 中传递的信息

按优先级排序（从最高到最低）：

| 优先级 | 信息类型 | 对应模板段落 | 为什么必须 |
|--------|---------|------------|----------|
| P0 | 被否决的方向/方案 | 不要做什么 | 恢复后最容易重蹈覆辙 |
| P0 | 参数/公式/信号模型约定 | 约定变更（新增） | 最高频丢失类型 |
| P1 | 不变量 | topic-index 活跃区域 | 跨对话架构约束 |
| P1 | 当前位置 | topic-index + handoff 下一轮 | 知道从哪里继续 |
| P1 | 范围边界（明确不含） | topic-index | 防止范围偏离 |
| P2 | 活跃债务 | 已知债务 | 防止遗忘技术债 |
| P2 | 决策引用 | 决策引用 | 决策有背景可查 |
| P3 | 历史进展摘要 | topic-index 历史区域 | 按需查阅 |

### 4.2 防止参数/公式约定变更丢失

**三层防护**：

**第一层：Handoff "约定变更"段（跨对话传递）**

每次写 handoff 时强制声明自上次以来的关键变更。无变更写"无关键变更"。

**第二层：topic-index "活跃约定"段（持久化）**

topic-index 活跃区域维护当前有效的关键约定列表：

```markdown
### 活跃约定

- 信号模型: r = sqrt(h) * s * exp(j*phi) + n, gamma = gamma_bar * h
- GG 参数: weak(4.0,3.0) / moderate(2.5,1.8) / strong(1.5,0.8) [Trinh 2017]
- SNR 约定: gamma proportional to h（相干检测），全文统一 [D010]
- 评估方法: resolve_qpsk 统一使用 [S026 重验确认]
```

每次约定变更时，同步更新此列表。旧约定不删除，而是标注"已废弃（D###）"。

**第三层：代码 SPEC.md（单一真相源）**

参数溯源系统（C2 方案）确保代码中的参数有来源标注。当参数变更时，SPEC.md 是最终真相源。topic-index 的"活跃约定"段只记录最关键的 5 条，细节指向 SPEC.md。

### 4.3 topic-index 维护检查清单

续接专题时，恢复对话应执行以下检查：

```
1. 读 topic-index "活跃区域"（≤50 行）
2. 确认"不变量"段无矛盾
3. 确认"活跃约定"与代码/SPEC 一致
4. 读最新 handoff 的"约定变更"段
5. 如有变更，在对话中确认理解后继续
```

写入 topic-index 时：

```
1. 更新"当前位置"（1-2 句话，覆盖旧内容）
2. 如有新不变量/约定，更新"活跃区域"
3. 在"历史区域"加 S###/R### 条目（1-3 行 + 成熟度标签）
4. 如有范围变更，更新"范围边界"并加"范围变更记录"
```

## 5. 专题生命周期管理改进

### 5.1 状态转换标准

| 状态 | 定义 | 进入标准 | 退出标准 |
|------|------|---------|---------|
| active | 正在推进 | 新建或续接 | 3 个对话未续接，或目标达成 |
| dormant | 暂停，可能续接 | 3 个对话未续接 | 续接（→ active）或确认放弃（→ closed） |
| closed | 已完成/已放弃 | 目标达成或明确放弃 | 不可逆转 |

**关键改进**：dormant 的进入标准从"用户说暂停"改为"3 个对话未续接"。这是自动触发，不依赖用户记忆。

**例外**：长期专题（framework-evolution、direction-scouting 等）不受 3 对话限制，只要 last_updated 在 30 天内就保持 active。

### 5.2 大型专题的拆分或归档策略

见 3.1 节"大型专题拆分标准"。补充操作流程：

1. **识别拆分时机**：session-governance 检测到专题 >50 文件或 >15000 行
2. **确定拆分点**：找自然边界（阶段转换、方向变更、子任务完成）
3. **创建子专题**：新目录 + 新 registry 条目 + depends_on 指向父专题
4. **冻结父专题**：父专题标 closed，topic-index 加"已拆分为 xxx, yyy"
5. **继承不变量**：子专题 topic-index 继承父专题的不变量

### 5.3 防止"已归档但仍标 active"的机制

**三层防护**：

1. **session-governance 自动检测**（见 2.2 节）：扫描 topic-index 关键词 + last_updated 时间
2. **写 handoff 时的状态确认**：session-governance 在写 handoff 时检查当前专题的状态是否合理
3. **开新专题时的依赖检查**：如果新专题 depends_on 一个 active 专题，但该专题的 topic-index 显示已完成，提示用户先关闭

## 6. 实施步骤
