## 1. 背景（理解即可，不要当结论照抄）

当前已知链条：

- 历史 D002 识别“混合分母”后，将 NDA、DA 和 selector 统一除以 1024，称 full/net BER，并据此报告 selector 相对固定 NDA 的低 SNR `+1.3~+2.3 dB`。
- 历史 D005/S007 随后明确：DA 错误只在 768 个 data bits 上计算，`ne_d/1024` 会把 256 个 pilot-related positions 隐式视作零错误；判断 DA/NDA 谁的标准 BER 更低时必须用 `ne_d/768` 与 `ne_n/1024`。该口径产生 26/29。
- R008/W002 后来同时使用上述两套结果：26/29 走 data BER，Fig.5 正值走 full/net；没有显式闭合两者的 metric-signature 冲突。
- R017 已明确写出 26/29 是“SW BER 离 DA_full 还是 NDA 近，推断选择，再与 data-BER 赢家比较”，说明它不是直接保存的 branch decision count。
- 当前 V007 追到 `_a4_switch_30seed_fixed.py`：selector 选 DA 时累计 768-bit population 的 `ne_d`，选 NDA 时累计 1024-bit population 的 `ne_n`，之后统一除以 1024。因此 `switch_ber_mean` 的 numerator population 随 branch choice 改变。
- 当前主控已拍板 D008：26/29 只作为 Results 中一次 aggregate selected-output alignment 辅助证据，不称 accuracy/recovery，也不写 26/26。
- 当前主控已拍板 D009：SNR 双坐标一次解释，以 2.5/2.4/3.1 dB total-energy-equivalent advantages 为主结果；这可能与 Fig.5 full/net 中对 pilot overhead 的处理发生重复记账，必须在本审计中检查。

以上只是待验证线索。执行方必须自行读原文件并核对。

### 2.1 必须回答的问题

#### A. 历史决策血缘

1. D002 所谓 Bug1“修复”具体改了 numerator、denominator 和比较对象中的哪些项？
2. D005 为什么又判 `DA_full=ne_d/1024` 不公平？它只推翻 branch winner 判定，还是逻辑上也推翻 D002 的 selector-vs-NDA metric？
3. D002/D005 是否存在正式 supersession？若没有，后续 R008/W002 如何把两者拼接？
4. R017 是否已经明确知道 26/29 是 aggregate proximity inference？若知道，为什么后续仍称 lower-BER estimator recovery？
5. 列出每一次结论变化的“为什么”与“为什么不采用另一口径”，不能只列时间线。

#### B. 指标签名与物理含义

对 NDA、DA-data、DA-full、selector、oracle 分别建立 metric-signature 表：

- numerator/error population；
- denominator；
- 每窗有效 payload bits；
- pilot positions 如何处理；
- branch choice 是否改变 numerator population；
- 数值单位与可比较条件；
- 可以使用的名称；
- 禁止支持的论文声称。

必须重点判断：

1. `switch_ber_mean` 是否是 BER、net BER、error density、decoded-error count per channel use，或上述均不是标准性能指标。
2. 将所有结果除以 1024 是否真正统一了统计总体，还是只统一了标度。
3. 该指标是否存在病态极端：例如发送更少/不发送 payload 会自动减少错误并被判更优。若存在，说明它能否承担“性能增益”。
4. Fig.5 的 `10log10(NDA/SW)` 中 1024 是否实际约掉；若约掉，所谓 full-block normalization 是否只是命名，不改变 error-count ratio 的本质。
5. D009 在 SNR 轴加入 1.249 dB pilot-energy term 后，再使用 Fig.5 full/net 口径是否构成 pilot overhead 的重复计算或概念混用。

#### C. 数值与数据充分性

1. 从现有 JSON 确定性复现 Fig.5 全部曲线及正文 2.3/2.0/1.3 dB 锚点，记录公式、字段和精确值。
2. 列出 JSON 是否保存：逐块 branch command、逐块 NDA/DA errors、共同 768 payload positions 上的错误、逐 seed branch counts、raw decisions。不得用“应该能”代替字段核查。
3. 判断以下指标能否仅用现有持久数据严格恢复，并逐项给 YES/NO + 证明：
   - 直接 selector branch-selection accuracy；
   - 三条路径统一 768-bit common-payload BER；
   - standard BER of selected output；
   - goodput/throughput；
   - branch-selection fraction；
   - aggregate alignment 26/29。
4. 若不能恢复，列出最小缺失字段；只设计未来重放合同，不执行。

#### D. 可投稿处理路线

至少比较以下四路，不得只给单一偏好：

1. 沿用历史 full/net BER reduction；
2. 改名保留为 error-density/error-count diagnostic；
3. 删除 Fig.5 的 selector-performance 角色或整图；
4. 未来统一 common-payload 后重放。

每路按以下维度评估：事实正确性、领域专业性、说服力、无 rebuttal 静默拒稿风险、对当前 3500+ 词/7 页版面的影响、是否需要新仿真、与 D008/D009 的兼容性。必须给出 stop/rejection criterion。

最后给一个推荐，但须明确：推荐基于什么；什么新证据出现时应改选其他路线。
