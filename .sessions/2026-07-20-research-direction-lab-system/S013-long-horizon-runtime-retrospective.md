### 2. 理想的协作形态

用户只承担极短中转：

1. 主控给出一句当前判断和一个 `T###` 路径；
2. 用户把路径交给新的 GLM 执行对话；
3. GLM 完成后只回传状态、commit、详细日志路径和一句关键异常；
4. 用户把这四项交回主控；
5. 主控直接从磁盘读取完整日志、artifact 和 Git 证据，审查后生成下一份 `T###`。

主控负责状态恢复、科学审查、战略判断、流程纠偏和下一任务；GLM 负责一个有界工作包。两者不得同时修改同一 worktree，也不得把用户当作人工状态同步器。

### 3. 四层记忆与唯一拥有者

| 层级 | 默认位置 | 唯一职责 |
|---|---|---|
| 当前快照 | `topic-index.md` / 项目 `STATUS` | 目标、当前阶段、唯一下一步、阻塞与关键指针 |
| 长程控制日志 | 本专题持续追加的 `S###` | 每轮为什么做、主控怎样裁决、目标轨迹怎样变化、下一轮为什么这样派 |
| 单项工作日志 | `projects/{project}/worker-logs/` | GLM 实际执行的命令、参数、尝试、失败、偏离、测试、修改文件和回传信息 |
| 原始证据 | batch/probe artifacts、代码、配置和 commit | 原始数字、逐样本数据、hash、合同和可复现材料 |

补充边界：

- `T###` 是不可变任务书，不是结果日志。
- `H###` 只服务于主控对话更换，不为每次 GLM 工作包生成。
- `D###` 只记录会改变路线、架构或接口的长期决策。
- `V###` 只记录关键晋级、撤回和独立验证，不替代工作日志。
- 长程日志只写裁决、变化和指针，不复制单项工作日志；轻量入口不能以删除细节为代价。

单项工作日志至少保留：任务书与起始 HEAD、冻结假设和否决条件、实际命令与参数、全部重要尝试、偏离及原因、结果与异常、修改文件、测试和独立审查、artifact/hash、最终 commit、未决项和下一步建议。

### 4. 对既有运行的待核验假设

本轮讨论没有把“此前缺少方法”简单归因于候选不够好。需要通过历史证据检验：

- 设计层已经包含候选族、批量探索、Probe→Scout→Deep Evidence 和论文收获，但实际运行中的优先级、所有权和工作包边界是否稳定兑现；
- “自动继续”是否退化为继续补治理、补状态、补 verifier，而不是持续提高找到论文方法的概率；
- 主控、GLM、Skill、项目状态和 `.sessions` 的职责是否在真实运行中发生重叠；
- 轻量 Probe 是否仍生成了过重的 S/D/V/H/synthesis 链，使过程产物远多于新增科学信息；
- current view、protected state、master-state 和多 worktree 是否出现过 visibility/ownership 冲突；
- Task 8/9 的预设行为测试是否未覆盖多轮真实科学运行中的目标漂移、过度深挖和工作量膨胀。

以上均是复盘问题，不是本文件已证明的最终根因。

#### B. 深读五类关键转折

1. 原有批量方法论怎样设计，哪些承诺后来实际没有兑现；
2. 第一个轻量、合法、确有信息增量的工作包；
3. 从轻量探索转向重型治理或基础设施的拐点；
4. F1/F3 等正信号被撤回、修正和 SCIENCE_FREEZE 的完整因果链；
5. current view、protected history、master-state 和多 worktree 发生冲突的链路。

#### C. 用统一问题审计

每个转折只回答：

1. 当时的论文目标是什么？
2. 为什么选择这项工作，而不是其他候选？
3. 一个对话实际完成了多少科学动作、产生多少治理动作？
4. 证据在哪一步失真、越级或失去可部署语义？
5. 哪项门控本应更早发现问题？
6. 哪项门控只是增加成本，没有改变科学判断？
7. 恢复后能否在五分钟内知道当前目标、dead ends 和唯一下一步？
8. 如果采用四层日志和单工作包制，这次失败是否能被提前截断？
