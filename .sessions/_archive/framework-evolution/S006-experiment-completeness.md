# [S006] 实验完备性缺口：框架缺少"审稿人视角"机制

> 2026-05-18 | 框架设计 | active

## 目标

识别框架在"实验设计完备性"方面的系统性缺口，确定调研方向，为后续框架增强做准备。

## 记录

### 问题起源

从 leo-congestion-routing Execute 漏洞审计对话（session 1840cd63）中观察到：6 项修复（F1 surge/F3 ECMP/M2 MLP/M3 统计/m4 指标/F4 泛化分析）全部是**事后发现**的，没有一项是框架在设计阶段就要求检查的。

用户直觉：框架跑完主线（GW→Contract→Execute），感觉离"能写论文"还差很远。很多对比维度、仿真验证是"拍脑袋"补的，没有系统指导。gw-read 的"写作架构提取"是观察性的（记录别人怎么写），但没有转化为对自身实验的可执行要求。

### 核心诊断

框架现在是**纵向主线**（GW→Contract→Execute），检查"方向行不行、假设对不对、代码跑没跑"。

但写论文需要**横向覆盖**——审稿人会问的所有维度。框架没有一个机制系统性地枚举和规划这些维度：

| 缺失维度 | 说明 | 漏洞审计中的对应 |
|---------|------|-----------------|
| 竞品实验矩阵 | 别人的论文都在比什么？我们是否覆盖了所有标准维度？ | F3: ECMP 实现不完整 |
| 声称-证据审计 | 论文每个 claim 需要什么级别的证据？现有实验是否逐条支撑？ | F4: 泛化声称验证的是什么？ |
| 指标完备性 | 这个子领域的标准指标有哪些？我们只报了哪些？ | m4: 只报 MLU，缺 CV/Overflow |
| 统计规范性 | 需要什么检验？种子数够不够？置信区间？ | M3: 完全没有统计检验 |
| 鲁棒性维度 | 参数敏感性、场景泛化、极端条件——哪些是领域惯例？ | F1: surge 参数训练/评估不一致 |
| baseline 合规性 | 每个 baseline 实现是否达到竞品论文的实现水平？ | M2: MLP 条件不公平 |

### 每项漏洞的框架拦截失败分析

|------|----------------------|------|
| F1 surge 训练/评估不一致 | Contract S3 参数溯源 | 只查"值哪来的"，没查"训练和评估是否用同一套参数" |

### 现有"写作架构提取"的局限

gw-read.md 的写作架构提取（H004 引入）关注**叙述层面**：章节结构、公式用法、引用模式、经典段落摘录。

缺失的是**证据层面**：每个声称需要什么实验支撑、什么指标证明、什么统计检验确认。前者解决"写得好不好"，后者解决"站不站得住"。

### 初步方案方向

**核心思路**：把竞品论文的实验设计系统性地提取出来，作为自身实验完备性的对标基准。

两步走：
1. **规范性**（"这个领域默认要做什么"）：统计检验、种子数、指标覆盖、baseline 数量——领域惯例，不做就被质疑
2. **针对性**（"我们的具体声称需要什么"）：声称泛化就需要跨规模实验，声称鲁棒就需要极端条件——跟具体论文声称有关

### 需要调研确认的问题

"声称-证据映射"的具体形态未定。可能的形式：

- **审稿人问题→证据**：逆向视角，"审稿人会问什么，我们有什么证据"
- **贡献→必要证据类型**：正向视角，"每个贡献需要什么类型的证据支撑"
- **论证结构**（Toulmin 模型）：claim + grounds + warrant + backing + qualifier
- **混合**：以上几种的组合

具体形态不能拍脑袋定，需要通过多角度调研确认。
